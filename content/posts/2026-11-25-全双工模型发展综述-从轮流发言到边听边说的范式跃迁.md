# 全双工模型发展综述：从轮流发言到边听边说的范式跃迁

> 本文系统梳理全双工语音/多模态模型从 2023 到 2026 年的发展脉络，覆盖核心论文、代表性模型、评测基准与应用场景。信息截止 2026 年 11 月。

---

## 一、什么是全双工？——从通信术语到交互范式

"全双工"（Full Duplex）借自通信领域，原指通信双方可以**同时发送和接收**信号。在语音交互语境下，它意味着 AI 可以**边听边说**——在持续生成回复的同时，仍然在实时处理用户的新输入。

这个看似简单的定义背后，是一个深刻的范式跃迁。

### 1.1 三种交互范式

| 范式 | 特征 | 代表 | 延迟 |
|:---|:---|:---|:---|
| **半双工** (Half-duplex) | 严格轮流：用户说完 → 系统处理 → 系统回复 | 传统 ASR+LLM+TTS 级联 | 2-5s |
| **伪全双工** (Pseudo-full-duplex) | 外部打断检测 + 级联：用户说话时系统能被打断，但不能同时处理 | FireRedChat、LiveKit | 1-3s |
| **真全双工** (True full-duplex) | 原生同时听说：编码和解码在同一处理周期内并行 | Moshi、Lychee-FD、GPT-Live | <500ms |

真全双工要求三个硬性条件同时满足：

1. **并发性**：在计算当前输出 token 时，同时摄入新的输入 token
2. **实时约束**：单步计算延迟 < 200ms
3. **自条件性**：生成依赖自身历史输出（实现回声消除和连贯性）

### 1.2 为什么全双工如此重要？

人类对话天然就是全双工的。两个人聊天时，听和说几乎从不严格交替——我们会重叠、打断、给出"嗯""对"这样的回应信号（backchannel）、在对方还在说的时候就开始组织自己的下一句话。

半双工系统把这些自然的对话动态全部抹平了。你必须在它说完之后才能开口，它也必须等你说完才能开始处理。这种"对讲机"式的交互，与人类对话的本质相悖。

全双工不是锦上添花，而是让 AI 对话**像人对话**的必要条件。

## 二、发展时间线——从 dGSLM 到 GPT-Live

### 2.1 萌芽期（2023-2024 H1）：证明全双工可以涌现

**2023 · dGSLM（Meta）**——第一个发现"涌现轮次转换"能力的模型。dGSLM 用双塔 Transformer 加交叉注意力，在没有任何显式轮次标注的情况下，模型自发学会了何时该听、何时该说。这个发现的意义在于：全双工对话的动态不需要人工设计，它可以**从数据中涌现**。

**2024.04 · Moshi（Kyutai Labs）**——第一个实时全双工语音基础模型，也是整个领域的里程碑。

- **7B 参数**语言模型骨干
- **Mimi 神经音频编解码器**：24kHz 音频压缩到 1.1kbps，12.5Hz 帧率
- **Inner Monologue（内心独白）**：模型在生成音频 token 之前，先预测与时间对齐的文本 token。这个"先想后说"的机制显著提升了生成语音的语言质量
- **双流并行**：同时建模用户音频流和助手音频流
- **理论延迟 160ms**，实际约 200ms
- 开源权重（CC-BY），提供 PyTorch/MLX/Rust 三套实现

Moshi 的核心贡献不仅是模型本身，更是**确立了全双工语音基础模型的研究范式**：神经音频编解码器 + 多流 Transformer + 文本辅助监督。后续几乎所有工作都站在 Moshi 的肩膀上。

**2024 · SALM-Duplex（沙特阿美）** 和 **Parrot（字节跳动）** 也在全双工方向做出了早期探索，分别在多流处理和对话动态建模上积累了经验。

### 2.2 爆发期（2024 H2-2025）：从研究走向产品

**2024 · GLM-4-Voice（清华/字节）**——首个中文全双工语音模型，证明了全双工范式在非英语语言上的可行性。

**2025.01 · Seed-Realtime（字节跳动）**——字节在实时语音交互上的重要布局，为后续豆包全双工产品奠定基础。

**2025.02 · FireRedChat（小红书）**——**业内首个可私有化部署的全双工语音交互系统**。

- 架构：交互控制器 + 交互模块 + 对话管理器
- 核心技术：自研 pVAD（个性化语音活动检测）+ EoT（语义回合结束检测）
- 性能：误打断率 10.2%（LiveKit 33.4%，Ten 78.1%）；端到端延迟 P50=2.341s
- 完全开源，支持本地一键部署，数据不出域

FireRedChat 的意义在于证明了全双工系统**不需要依赖云端 API**，企业可以在私有环境中安全部署。

**2025.09 · Qwen3-Omni（阿里通义）**——首个在文本、图像、音频、视频四模态上均保持 SOTA 的单一多模态模型。

- **Thinker-Talker MoE 架构**：Thinker 负责文本语义理解与生成，Talker 专注实时语音 token 生成
- 30B 参数，3B 激活（MoE）
- 端到端理论首包延迟 **234ms**
- 36 项音视频 benchmark 中 22 项整体 SOTA
- 支持 119 种语言文本交互、19 种语言语音理解、10 种语言语音生成
- Apache 2.0 开源

Qwen3-Omni 证明了"全模态不降智"的可行性——不需要为了语音能力牺牲文本或视觉性能。

**2025.09 · Gemini Live（Google）**——Google 的实时语音 API，支持 70 种语言、实时插话、工具调用、即时翻译。通过 WebSocket 协议提供有状态的流式连接，成为全双工语音商业化的重要推动者。

### 2.3 成熟期（2026）：百花齐放与范式分化

2026 年是全双工模型的"寒武纪大爆发"。仅上半年就有数十个重要模型和系统发布：

**2026.03 · MiniCPM-o 4.5（面壁智能/清华）**——Omni-Flow 三流时间对齐架构，9B 参数端侧部署，<12GB 显存，边看边听边说的全双工能力。

**2026.03 · MOSS-VL（清华）**——L5 级"边说边看"交互，48 层混合架构（36 self-attn + 12 门控交叉注意力），XRoPE 三轴位置编码，绝对时间戳 token。

**2026.05 · JoyAI-VL-Interaction（京东）**——每秒三选一决策（沉默/响应/委托），AdaCodec 预测编码，三层记忆架构（约 2 小时上下文），人评对豆包 77.6%/Gemini 87.9%。

**2026.06 · Lychee-FD（哈工大深圳）**——**ACL 2026 杰出论文奖**（获奖比例约 0.15%）。

- 首次揭示全双工 SLM 性能下降的根本原因：声学与语义建模共享深层参数时的**梯度冲突**
- 层次化参数分离策略：浅层共享主干，深层拆分为语义/声学/对话控制专门通道
- 语义对齐通道维持跨模态一致性
- Spoken QA 提升 7.4%，FullDuplexBench 1.5 提升 28.5%
- 开源框架、训练流水线和模型权重

**2026.07 · NemotronLabs VoiceChat（NVIDIA）**——12B 参数全双工语音模型，**首个原生支持工具调用的开源全双工模型**。

- 流式语音编码器 + decoder-only LLM + 并行输出流（文本 + 函数调用）+ 辅助 RNN-T 转录分支 + 流式 TTS 解码器
- Full-Duplex-Bench 1.0 最低暂停处理接管率
- 用户打断后 100% 接管，打断后回复质量 4.33/5
- FDB 3.0 工具选择 F1 82.5%
- 目标端到端延迟 < 300ms

**2026.09 · TASTE2（联发科/台大）**——文本对齐语音建模路线，将 TASTE 从单句级扩展到增量对话栈，实现流式合成与打断处理。

**2026.09 · GPT-Live-1（OpenAI）**——**全双工语音商业化的里程碑**。

- 首个面向开发者开放的全双工语音 API
- 定价 **\$0.05/分钟**（语音层），后端模型另计
- Full Duplex Bench 较 GPT-Realtime-2.1 提升 30 个百分点
- 轮换延迟从 1.4s 降至 0.8s
- 工具调用准确率从 60% 提升至 87%
- 12 种预设音色，支持电话场景
- 支持将推理和工具调用委托给 GPT-6 Astra 等后端模型

GPT-Live-1 的意义不仅在于技术指标，更在于它**定义了全双工语音的商业模式**：按分钟计费的语音层 + 按 token 计费的后端推理层。

**2026.09 · AdaptDuplex**——在 Qwen3-Omni 基础上引入自适应机制，动态预测窗口时长，训练免推理时控制（logits bias），在 Full-Duplex-Bench 和 HumDial-FDBench 上达到领先水平。

**2026.09 · DuplexCascade / MoshiRAG**——分别探索级联架构的优化和检索增强在全双工中的应用。

### 2.4 具身化（2026 H2）：全双工走出屏幕

**2026.09 · MIRA**——首个全双工人形机器人交互框架，部署在 Astribot S1 人形机器人上。

- CORTEX 双时间尺度交互策略：低延迟抢占 + 审慎轮次决策
- ROSCO 前缀条件扩散模型：流式音频到关节动作生成
- 物理安全约束：执行层在控制频率上强制执行安全限制

**2026.11 · DyaPlex（NVIDIA）**——全双工语音-动作模型，单一模型同时生成语音和手势。

- 冻结的全双工语音塔（PersonaPlex）+ 可训练的因果动作塔
- 时间对齐的语音-动作 RoPE 引导跨注意力
- 可用于人-机器人交互和人-Agent 交互

**2026.11 · EIP（Embodied Interaction Policy）**——统一流式框架，通过逐层联合注意力将音频-交互专家与动作专家耦合。

- 400ms 时间粒度的分块因果处理
- 语音 token 编码说话状态和语义情感
- 热启动延迟降低 64%

## 三、架构分类——四条技术路线

全双工模型的架构设计是整个领域最核心的分歧。根据对"听"和"说"的耦合方式，可以分为四条路线：

### 3.1 级联式（Cascaded）

```
用户语音 → [ASR] → 文本 → [LLM] → 回复文本 → [TTS] → 语音
                    ↑
              [外部打断检测]
```

**代表**：FireRedChat、LiveKit、传统 IVR 系统

**优点**：模块化、易调试、可独立替换各组件、可复用现有成熟模型

**缺点**：延迟高（每个环节都加延迟）、交接抖动、无法真正同时听说

**适用场景**：对延迟不敏感的企业客服、需要严格数据合规的私有化部署

### 3.2 Thinker-Talker 解耦

```
用户语音 → [Audio Encoder] → 
    Thinker（文本推理 + 工具调用）→ 文本 token
    Talker（语音生成）→ 音频 token → [Vocoder] → 语音
```

**代表**：Qwen3-Omni、Moshi（inner monologue）、GPT-Live-1 + 后端模型

**优点**：保留强大的文本推理能力、可委托给不同能力的后端模型、工具调用成熟

**缺点**：推理成本高（两个模型并行）、语音层与推理层的延迟叠加

**核心洞见**：GPT-Live-1 的架构选择揭示了一个重要趋势——**语音层不需要自己做推理**。把深度思考交给后端大模型，语音层专注于"听"和"说"的节奏控制，反而能获得更好的交互体验。

### 3.3 原生端到端全双工

```
用户音频流 → [统一多流 Transformer] → 助手音频流
                  ↑
            同时建模听说
```

**代表**：Lychee-FD、MiniCPM-o 4.5、MOSS-VL

**优点**：最低延迟、最自然的交互节奏、无交接损失

**缺点**：训练复杂（需要大量同步对话数据）、模态干扰（声学/语义梯度冲突）、语义理解能力可能退化

**Lychee-FD 的关键发现**：声学与语义建模在共享深层参数时会产生梯度冲突，导致"模态干扰"。解决方案是层次化参数分离——浅层共享学习底层表示，深层拆分为专门通道。这一发现为整个原生全双工路线提供了理论指导。

### 3.4 多流并行 + 时间对齐

```
用户音频流 ──→ [并行编码] ──→ [时间对齐注意力] ──→ 
助手音频流 ──→ [并行解码] ──→ [时间对齐注意力] ──→ 输出
```

**代表**：Moshi、StreamingVLM、JoyAI-VL-Interaction

**优点**：训练-推理一致性（训练时的模式就是推理时的模式）、可扩展到长时流

**缺点**：需要大量时间对齐的同步数据、对位置编码要求高（需要处理连续时间）

**核心洞见**：训练-推理一致性是全双工模型的**隐藏主线**。StreamingVLM 用重叠短块训练模拟推理 pattern，Moshi 用双流并行，JoyAI 用每秒三选一决策——方法不同，但都在追求"训练时怎么听说的，推理时就怎么听说"。

## 四、评测基准——如何衡量"像人"

全双工评测是整个领域最碎片化的部分。传统的 ASR/LM 指标（WER、BLEU、MMLU）无法捕捉全双工交互的核心体验——**时机感**。

### 4.1 主流 Benchmark 一览

| Benchmark | 版本 | 评测维度 | 备注 |
|:---|:---|:---|:---|
| **Full-Duplex-Bench (FDB)** | v1.0 | 基础轮次转换、暂停处理 | 最主流的全双工评测 |
| | v1.5 | +backchannel、overlap、交互流畅度 | 增加自然对话动态 |
| | v3.0 | +工具调用（tool-selection F1） | 2026 新增 |
| **FullDuplexBench 1.5** | - | 交互流畅度综合评分 | Lychee-FD 在此提升 28.5% |
| **VoiceBench** | - | 语音理解、推理、多语言 | 归一化平均分 |
| **HumDial-FDBench** | - | 人类录音对话评测 | 最接近真实人评 |
| **Spoken QA** | - | 语音问答准确率 | 衡量语音智能 |
| **τ-Voice** | - | 延迟相关评测 | 关注时序性能 |
| **Duplex-MPE** | - | 多轮对话评测 | 关注对话连贯性 |
| **MTR-DuplexBench** | - | 多轮对话 | 关注轮次管理 |
| **Talking Turns** | - | 轮次转换质量 | 关注时机决策 |
| **OVO** | - | 边说边看能力 | MOSS-VL 70.2 |
| **OmniMMI** | - | 多模态交互 | MOSS-VL 32.7 |
| **ProactiveVideoQA** | - | 主动视频问答 | MOSS-VL 47.2 |
| **LiveSports-3K-CC** | - | 体育解说 | MiniCPM-o 4.5 54.4 |

### 4.2 评测的关键挑战

**1. 同步数据稀缺**：全双工评测需要真正的双人同步对话数据（两个说话人的音频在时间上精确对齐），这类数据远比单句语音数据稀缺。

**2. 主观性强**：全双工交互的"自然感"高度主观，自动化指标与人类感受之间的鸿沟仍然很大。HumDial-FDBench 和真实人评的出现是对这一挑战的回应。

**3. 维度爆炸**：全双工交互涉及轮次转换、打断处理、backchannel、重叠语音、情感表达、语义连贯等多个维度，单一指标无法全面衡量。

**4. 评测转向真实人评**：2026 年的明显趋势是从纯自动化 benchmark 转向人类评测。JoyAI 的人评（对豆包 77.6%、对 Gemini 87.9%）、HumDial-FDBench 的出现都反映了这一趋势。

## 五、应用场景——全双工落地在哪里

### 5.1 电话客服与语音 Agent

这是全双工语音**商业化最成熟**的场景。

- **Yelp**：集成 GPT-Live-1 后，电话预订场景中点餐转化率提升 13%，用户用更完整自然的句子交流
- **EliseAI**：医疗语音助手，代码库精简 80%，删除 2.3 万行代码
- **Cognition (Devin)**：集成 GPT-Live-1 后语音会话次数增加 40%，合并 PR 数量增加 60%

全双工在客服场景的核心价值：**不需要等 AI 说完就能补充信息或改变主意**，这让电话交互从"跟机器说话"变成"跟人说话"。

### 5.2 语言学习与教育

- **Speak**：GPT-Live-1 让学习者在停顿思考时被打断的次数减少近 80%

全双工在教育场景的核心价值：**AI 能区分"我在思考"和"我说完了"**，不会在你还在组织语言时就急着开口。

### 5.3 人形机器人与具身交互

2026 年下半年最引人注目的新方向。

- **MIRA**（Astribot S1 人形机器人）：全双工对话 + 流式手势生成 + 物理安全约束
- **DyaPlex**（NVIDIA）：单一模型同时生成语音和手势，支持人-机器人和人-Agent 交互
- **EIP**：统一流式框架，热启动延迟降低 64%
- **Lychee-FD + Shennie 情感机器人**：无唤醒词、实时反馈的"在场"对话体验

具身交互对全双工的要求比纯语音更高：不仅要同时听说，还要**同步生成身体动作**，并在被打断时**安全地停止物理运动**。

### 5.4 数字人与虚拟形象

- **Lychee-FD + Soul-LiveAct**：语音、口型、表情和回应节奏围绕同一段连续对话同步发生
- **Gemini Live**：支持智能眼镜、车载等新一代界面

### 5.5 实时翻译

- **Gemini Live**：70+ 语言实时翻译，低延迟
- **GPT-Realtime-Translate**：OpenAI 的流式语音翻译模型

### 5.6 编程助手

- **Heard**：为 Claude Code 等 Coding Agent 加上语音层
- **Qoder Voice**：全双工语音 Agent

## 六、六条核心洞见

### 洞见一：竞争焦点从"看得懂"转向"时机决策"

早期全双工模型的核心挑战是"听懂用户在说什么"。到 2026 年，语音识别和语义理解已经基本解决，竞争焦点转向了**"什么时候该开口、什么时候该闭嘴、什么时候该被打断"**。

JoyAI 的每秒三选一决策、AdaptDuplex 的自适应窗口、MOSS-VL 的绝对时间戳——都在解决同一个问题：**时机决策**。

### 洞见二：训练-推理一致性是隐藏主线

StreamingVLM 用重叠短块训练模拟推理 pattern，Moshi 用双流并行，Lychee-FD 用原生端到端——方法不同，但都在追求"训练时怎么听说的，推理时就怎么听说"。违反这一原则的模型（如训练时单句、推理时流式）在全双工评测中普遍表现不佳。

### 洞见三：沉默是头等公民

全双工模型不仅要学会"说什么"，更要学会"什么时候不说"。JoyAI 的 </silence> token、MOSS-VL 的 turn-final end token 屏蔽、GPT-Live-1 的暂停处理——都在教模型**沉默的价值**。

一个不会沉默的 AI，比一个不会说话的 AI 更让人烦躁。

### 洞见四：语音层不需要自己做推理

GPT-Live-1 的架构选择——语音层 + 后端推理模型委托——揭示了一个重要趋势。语音层专注于"听"和"说"的节奏控制，深度思考交给后端大模型（GPT-6 Astra、Luna 或第三方），反而能获得更好的交互体验。

这与人类对话的模式一致：我们说话时，"说什么"和"怎么说"是两个相对独立的 process。

### 洞见五：端侧是默认终局

MiniCPM-o 4.5 的 <12GB 端侧部署、Lychee-FD 的单 GPU 推理、FireRedChat 的私有化部署——都在指向同一个方向：**全双工最终要跑在用户设备上**。

原因很简单：全双工对延迟极度敏感（<200ms），任何网络往返都是不可接受的。

### 洞见六：评测从自动化转向真实人评

Full-Duplex-Bench 从 v1.0 到 v3.0 的演进、HumDial-FDBench 的出现、JoyAI 的大规模人评——都反映了领域共识：**自动化指标无法全面衡量全双工交互的体验**。

一个在 FDB 上得分很高的模型，可能在真实对话中让人感觉很"机械"。评测必须跟上。

## 七、展望——下一步去哪里

### 7.1 多人对话

当前所有全双工模型都假设**一个用户 + 一个 AI**。真实场景中，多人对话（会议、群聊、家庭对话）是更常见的需求。这需要模型能区分多个说话人、处理多方轮次动态。

### 7.2 长时记忆与上下文

JoyAI 的三层记忆架构（约 2 小时上下文）是第一步，但远远不够。全双工交互的上下文管理需要新的范式——不是简单的"记住更多"，而是"记住重要的"。

### 7.3 情感与共情

Lychee-FD 的情绪探测实验表明，全双工模型的内部表示确实编码了情感信息。如何将这些信息显式地用于情感感知和共情回应，是下一个重要方向。

### 7.4 多模态全双工

从"边听边说"到"边看边听边说边做手势"——MOSS-VL、JoyAI、MIRA、DyaPlex 已经开始了这个方向。未来的全双工模型将是**全模态**的：同时处理视觉、听觉、触觉，同时生成语音、文本、动作。

### 7.5 L5 基准缺失

MOSS-VL 定义的 L5 级"边说边看"交互，目前还没有标准化的评测基准。随着更多 L5 模型的出现，建立 L5 基准将是领域的重要任务。
